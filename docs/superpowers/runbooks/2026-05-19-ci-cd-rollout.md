# GitHub Actions CI/CD Rollout — Manual Steps

**Companion to:**
- Spec: `docs/superpowers/specs/2026-05-19-github-actions-ci-cd-design.md`
- Plan: `docs/superpowers/plans/2026-05-19-github-actions-ci-cd.md`
- Branch: `feat/github-actions-ci-cd`

This document captures the manual / browser steps that subagent-driven implementation could not perform. The order below matters mostly because of one chicken-and-egg: branch protection can't require status checks that haven't run once, so `main` is protected AFTER the first successful CI + release, not before.

Most of the work is one-time configuration in two browser tabs (npmjs.com and github.com). The reason it can't be automated end-to-end is OAuth: `npm login` opens a browser, npm Trusted Publishers is configured through the npm web UI, and GitHub Environments / branch protection live in repo Settings. Once it's done you don't have to touch any of it again.

---

## 1. Finish the in-flight 0.2.0 release

The local `main` has a committed-but-unpublished `0.2.0`. Ship it the old way before CI takes over.

```
npm login           # interactive; opens a browser tab
npm whoami          # should print your username, not 401
git checkout main && pnpm publish --access public && git push --follow-tags
```

Verify:
```
curl -s https://registry.npmjs.org/medusa-plugin-printify | jq -r '."dist-tags".latest'
# expected: 0.2.0
```

## 2. Configure npm Trusted Publisher

Go to `https://www.npmjs.com/package/medusa-plugin-printify/access` → **Add Trusted Publisher** → **GitHub Actions**. Enter:

| Field | Value |
|---|---|
| Repository owner | `greedychipmunk` |
| Repository name | `medusa-plugin-printify` |
| Workflow filename | `release.yml` |
| Environment name | `npm-publish` |

Save. npm now trusts publish requests originating from this exact workflow + environment.

## 3. Create the `npm-publish` GitHub Environment

Go to `https://github.com/greedychipmunk/medusa-plugin-printify/settings/environments` → **New environment** → name it exactly `npm-publish`.

Under **Deployment branches and tags**: choose **Selected branches and tags**, add a rule for `main`. (Optional: add yourself as a required reviewer if you want a human gate before every publish — leave empty for solo workflow.)

## 4. Push the branch and open the release PR

From the repo:

```
git checkout feat/github-actions-ci-cd
git push -u origin feat/github-actions-ci-cd
```

Open the PR with a `feat:` title so the first auto-release is a minor bump (`0.2.0` → `0.3.0`):

```
gh pr create \
  --base main \
  --title "feat: github actions ci/cd with trusted publisher" \
  --body "$(cat <<'EOF'
## Summary

- Add `ci.yml` running tests, build, PR-title lint, and version-field-guard on every PR.
- Add `release.yml` that parses the merged PR's conventional-commit title and auto-publishes the matching semver bump to npm via Trusted Publishers (OIDC), then tags and creates a GitHub Release.
- Add `compute-bump.sh` and shell-based tests for the bump-decision logic.
- Add PR template nudging contributors to the conventional title format.
- Remove obsolete `release:*` scripts from `package.json` (CI is now the sole release authority).

## Test plan

- [ ] CI workflow runs on this PR with `test`, `pr-title-lint`, and `version-field-guard` all green.
- [ ] After merge, `release.yml` publishes a `0.3.0` minor release with provenance.
- [ ] Tag `v0.3.0` exists on origin and a GitHub Release page is created.
EOF
)"
```

Watch the three CI checks (`test`, `pr-title-lint`, `version-field-guard`) go green, then merge. The release workflow will:
1. Parse the `feat:` prefix → minor bump.
2. Bump `package.json` to `0.3.0`.
3. Install / test / build.
4. Publish to npm via OIDC with provenance attestation.
5. Commit the bump back to `main` and push tag `v0.3.0`.
6. Create a GitHub Release with autogenerated notes.

Verify:
```
curl -s https://registry.npmjs.org/medusa-plugin-printify | jq -r '."dist-tags".latest'
# expected: 0.3.0
gh release view v0.3.0
```

The npmjs.com package page should show a "Provenance" badge on `0.3.0`.

## 5. Enable branch protection on `main`

Now that all three CI checks have run at least once, they're selectable as required checks. Go to `https://github.com/greedychipmunk/medusa-plugin-printify/settings/branches` and add a rule for `main`:

- Require a pull request before merging: ✅
- Require status checks to pass: ✅
  - Require branches to be up to date: ✅
  - Required checks: `test`, `pr-title-lint`, `version-field-guard`
- Allow `github-actions[bot]` to bypass — needed so `release.yml` can push the bump commit and tag directly to `main` after merge.

## Follow-up recommendations (not blockers)

Two notes from code review worth tracking after the initial rollout:

- **Pin actions to commit SHAs.** Currently `actions/checkout@v4`, `pnpm/action-setup@v4`, `actions/setup-node@v4`, `amannn/action-semantic-pull-request@v5`. For a public npm package, SHA-pinning plus Dependabot keeping them current is the supply-chain-hygiene best practice. Reasonable follow-up PR.
- **Double build in release.yml.** The explicit `pnpm build` step plus `prepublishOnly` means the plugin builds twice per release (~30-60s wasted). Acceptable as defensive layering; could be collapsed to one step if you prefer.
